# CausativeLens v0.1.2 Beta：证据级采集与因果履约方案

语言切换：[English](v0.1.2.en-US.md) · [简体中文](v0.1.2.md)。

## 先把承诺说清楚

v0.1.2 仍然是 `v1.0.0` 之前的测试版，目标不是增加更多按钮，而是让 CausativeLens 第一次能够对一条真实 Windows 会话给出可复核的回答：

> “第 7 步推理声明要只读 `config.yaml`；同一进程树中，ETW 在这段时间看到了哪些事实？这些事实是否足以判定履约、偏离、未观测，还是因为采集缺口只能判定为未知？”

因此 v0.1.2 定位为 **Evidence-grade capture & causal verification Beta**。没有真实 ETW、TDH 对照、跨进程恢复和证据包，就不把 v0.1.2 标成“内核监控已完成”。v0.1.1 的 GUI 监听结果仍然保留，但必须继续标注为 runtime report；它不能冒充 kernel evidence。

## 只交付一个纵向闭环

v0.1.2 只承诺 x64、Windows 10 1809+ / Windows 11、当前用户本机、`observe` 模式。以下闭环必须从双击 GUI 或一条 CLI 命令完整走通：

```text
选择 Harness 目录
  → 标准用户 clens-daemon 建会话
  → 仅 clens-capture 通过 UAC 建四条 ETW 会话
  → Process/File/Registry/Network EVENT_RECORD 解码
  → 16 轮时钟锚定 + QPC 重排
  → mmap ring；95% 后无阻塞转入 .clspool
  → daemon 读取 Harness JSONL，规则层生成 Assertion
  → 进程树 + 时间 + 语义 + 路径/端点四维对齐
  → SQLite 履约图与证据包
  → clens why / GUI Graph 给出五段式因果链
```

如果其中任何一站没有运行态证据，界面显示“未接通/不可判定”，而不是绿色成功。

## 面向极客的三个生产力工作流

以下命令是 v0.1.2 的目标接口；它们在 v0.1.1 中尚不可用，不应写进当前版本的能力宣传。

### 1. 一条命令抓问题

```powershell
clens watch --runtime openclaw --trace-dir "$env:USERPROFILE\.openclaw\logs" --path .\case
```

`watch` 做四件事：检查适配器和日志 schema，启动 daemon，申请 capture UAC，实时显示 ETW/JSONL/gap/clock 状态。停止时生成 `case.cllens`、`case.clspool` 和证据摘要。没有管理员权限时给出 `CL-1001` 的具体动作，不会偷偷退化为“只看日志却显示正在监控”。

### 2. 直接回答“它为什么这样做”

```powershell
clens why --session .\case.cllens --path C:\work\config.yaml --json
```

返回固定五段：触发断言、证据事件链、履约/偏离/未观测判定、反向归因、置信度与采集健康度。每个 ETW 事实带 provider、event id/opcode/version、seq、QPC/UTC、pid/tid、解码路径（manual/TDH/unknown）和是否 rundown。

### 3. 把一次事故变成可分享的复现包

```powershell
clens pack --session .\case.cllens --out .\case.causative.zip
clens verify .\case.causative.zip
clens diff .\baseline.causative.zip .\regression.causative.zip --path config.yaml
```

证据包包含 schema/版本、clock anchor、provider 配置、decoder coverage、loss/gaps、Harness 原文哈希、断言、判定和必要的原始事件块；默认不包含文件内容、网络载荷或模型秘密。`pack` 可选路径/命令行脱敏，`verify` 校验 CRC、seq 连续性、manifest 哈希和证据签名。

## 采集实现方案

### 真实 ETW 控制面

生产 capture 不再调用 `logman` 创建会话。`logman` 只保留为诊断和 provider 自检工具。Windows 实现使用 `windows-rs`：

1. `StartTraceW` 为 Process、File、Registry、Network 建立四条独立 realtime session，名称保持 `CausativeLens_Process` 等契约。
2. `EnableTraceEx2` 按 provider GUID、已验证的 manifest keyword 和 PID 过滤启用事件；keyword mask 由 Windows runner 的 manifest 查询结果生成，不能靠记忆常量。
3. 每条 session 一个 `ProcessTrace` 消费线程，回调只做边界检查、复制必要的 EVENT_RECORD 元数据并投递到该 provider 的无锁队列；不在回调中访问 SQLite、网络或模型。
4. 控制线程每 500ms 查询 ETW session statistics，记录 `EventsLost`、`RealTimeBuffersLost`、buffer 数量和回调丢弃数。
5. Process/File session 建立后发出 capture-state/rundown 请求；补发事实统一带 `is_rundown=true`，只用于状态补全，不作为观测窗口内的履约证据。

capture 仍然是最小特权进程：不读用户输入、不联网、不执行策略。只有它请求 UAC，daemon、CLI 和 GUI 保持标准用户权限。

### 手工解码与 TDH oracle

解码键固定为 `(provider_guid, event_id, version, opcode, task)`，不能只按 opcode 猜布局。每个 decoder 分三层：

- **cursor 层**：对 EVENT_RECORD 的 user data 做长度检查、UTF-16 边界检查和 little-endian 读取；正常事件不分配字符串，路径进入 `PathInterner`。
- **语义层**：Process/File/Registry/Network 映射到 `SysEvent`，记录 FileObject、DesiredAccess、IO length、端点和 rundown 位。
- **未知层**：版本或 opcode 未知时保存受限原始字段摘要和哈希，产生 `UnknownEvent` 健康事实；不能静默丢弃，也不能把猜出的字段写成确定事实。

每个手工 decoder 都有同一 `EVENT_RECORD` fixture 的 TDH oracle。TDH 使用 `TdhGetEventInformation` 和 `TdhFormatProperty` 读取字段；CI 逐项比较字段名、类型、长度、UTF-16 文本、FileObject、pid/tid、QPC、rundown 标记。手工解码失败时只允许回退 TDH，回退路径和耗时必须写入证据。

FileObject 表采用 28 分片、TTL/LRU 上限和周期清扫；Create 建立映射，Rename 更新，Close 删除。FileRead/FileWrite 永远只记录长度和属性，不记录文件内容。

### QPC/UTC 时钟

ETW 使用原生 QPC tick；不能把 tick 值口头称为“已经是 100ns”。v0.1.2 保留旧 `ts_qpc` 字段，新增会话级 `clock_domain=qpc_ticks`、`qpc_frequency_hz`、`utc_anchor_100ns`、`anchor_error_100ns` 和 `sample_count`。派生的 UTC 只在存在 anchor 时写入。

启动时连续 16 轮：读 QPC、读 `GetSystemTimePreciseAsFileTime`、再读 QPC；选往返间隔最小的一轮作为 anchor，并记录全部样本摘要。每 60 秒双向心跳校准一次；漂移超过 `200µs/s` 刷新 anchor 并写入 `ClockCalibration` 事实。验收关注“测出来的误差是多少”，不把环境不稳定伪装成精确。

### ring 与 `.clspool`

使用 `CreateFileMappingW(..., SEC_COMMIT)` 创建 256MiB 单写单读 ring，命名事件负责通知，不轮询。header 采用固定布局和 cache-line 对齐的原子进度槽：magic、schema、writer/reader position、dropped、heartbeat、last committed seq。写者先写 frame，再以 Release 更新 commit position；读者以 Acquire 读取并回写消费位置。

frame 保留现有 magic/schema/CRC 兼容，同时增加 `seq_first/seq_last`、QPC 范围、event count、raw/compressed length、path snapshot id 和 frame CRC。ring 使用量达到 80% 发出 health warning，达到 95% 后直接写 `.clspool`，绝不阻塞 ETW 回调。spool 恢复按 frame 边界扫描：有效帧继续投递，损坏或截断位置写入 `gaps.json`；daemon 以 `seq` 幂等去重。

必须有真实测试：启动 capture，制造 10,000 个可预测文件/网络/注册表事实，杀死 daemon 或 capture，重启后继续读取，结果中的 seq、CRC、gap 和 verdict 与预期逐项相等。

## 因果履约层的生产化

### 断言必须带来源和主体

规则层先行：工具调用 `read/edit/shell/connect` 编译为断言；语义层仍是显式 `--extractor=llm` 的可选能力。每条 Assertion 保存 Harness 文件哈希、line/byte span、step、raw quote、提取器版本和主体 pid 绑定状态。

主体绑定优先使用 `run` 返回的 root pid；shell 工具调用按父 pid、时间邻接和 token Jaccard 锚定子进程。无法锚定时显示 `process_context=unknown`，降低分数，不得假装归因成功。

### “未知”要和“没有发生”分开

现有 `Fulfilment::Unobserved` 保持兼容，v0.1.2 另存 `visibility`：`complete`、`buffer_loss`、`filtered`、`decoder_unknown`、`capture_not_connected`。只有 `complete` 才能把窗口关闭解释为“未观测到”；其余情况统一显示“证据不可见”。这是避免误报和过度自信的关键。

### 真实证据的五段式输出

`why` 和 GUI Graph 使用相同 RPC：

1. 触发断言：step、raw quote、目标、期望、主体进程；
2. 证据事件：seq、UTC/QPC、provider、event id/opcode/version、pid/tid、路径/端点；
3. 判定：Fulfilled / Deviated / Partial / Unobserved，四维分数和水位线；
4. 反向归因：同一事实被哪些断言吸收，哪些事实是 superfluous；
5. 健康度：clock error、loss、gap、decoder coverage、rundown 和过滤说明。

## 适配器策略：少而真，其他可扩展

17 家模板继续保留，但 v0.1.2 不宣称 17 家厂商版本认证。真实端到端认证优先顺序为 Hermes Agent、Claude Code、OpenAI Codex、OpenClaw、Manus，加一个 Generic JSONL；其他模板提供路径发现、schema fingerprint 和未知字段 quarantine。

每次 `watch` 生成 adapter fingerprint：可执行文件版本、日志根路径、最近写入文件、schema keys 哈希和适配器版本。上游格式改变时，sentinel CI 先报“schema changed”，并保留 raw line；不会静默把错误字段编译成断言。这样极客可以自己添加一个适配器 fixture，而不必等待 CausativeLens 发布新二进制。

## 对极客真正有用的原因

这个版本的价值不是“看到了更多日志”，而是把一次 Agent 事故压缩成可重放、可审计、可分享的因果对象：哪一步说了什么、哪个进程做了什么、两者为什么被认为相关、采集是否完整、结论在哪些地方必须保持谦逊。它让调试者可以在终端里追到一个 seq，在 GUI 里看同一条证据边，在 CI 里用同一份 evidence pack 阻止回归。

望远镜先要把焦距校准。v0.1.2 的任务，就是让这架望远镜第一次真正对准内核轨迹。

## 可选 Jev／大模型辅助层（当前已接入，仍是 observe-only）

当前工作区已经提供 `clens-assist`，CLI 和 GUI 都通过 daemon 的 `assist.analyze` RPC 使用它。Jev 是默认 provider 名称，但 endpoint 与 model 由用户配置，不在客户端硬编码未经确认的服务地址；同时支持 OpenAI-compatible、Anthropic-compatible 与本机 Ollama。

辅助层只消费确定性查询已经得到的因果链：它不能读取会话目录、不能修改 `Verdict`、不能启动进程、不能执行 advise/enforce/decision。发送前默认把路径替换为稳定哈希、删除 `raw_quote`，并限制 prompt 为 48 KiB；API key 只在本次 CLI/GUI 进程或 RPC 请求内存中存在，绝不落入 settings 文件。模型返回的每条 finding 必须引用提交链中已有的 assertion id 或 event seq，否则整体标记为 `grounded: false` 并附 caveat。

CLI 示例：

```powershell
clens assist --enable --provider jev --endpoint https://your-jev-endpoint.example/v1/chat/completions --model jev-causal
$env:CAUSATIVELENS_LLM_API_KEY = 'session-only-key'
clens why --path config.yaml --assist
```

GUI 的“设置”页保存 provider、endpoint、model、token/温度/超时、路径脱敏、raw quote、查询后自动分析、时间线刷新和保留条数等选项；API key 输入框只保留在当前 GUI 进程。网络不可用或 provider 输出非 JSON 时，会保留明确的 ungrounded note，而不是伪装成履约结论。
