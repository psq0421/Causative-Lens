# CausativeLens v0.2.5：让 Agent 的一句“我要读 config.yaml”接受系统事实的检验

> 这是该项目迄今最大的一次更新。

很多 Agent 工具都能告诉我们“模型说了什么”，很多系统工具都能告诉我们“进程做了什么”。真正难回答的问题却在两者之间：模型在第 7 步说“我要以只读方式读取 `config.yaml`”，第 8 步系统究竟做了什么？如果同一个进程随后写入了这个文件，这应该被解释为一次普通写操作，还是一次推理承诺的偏离？

CausativeLens 的答案不是再做一张事件列表，而是建立一条可复核的因果证据链：**把 Agent 的推理步骤编译成因果断言，再到系统轨迹中逐条验证这些断言是否成立。**

这篇文章介绍 v0.2.5 的工作机制、架构边界、代码规模和实际使用方式，也把当前版本还没有证据证明的地方写清楚。

## 一、它解决的是哪一个空白

Agent 的 Harness 日志和操作系统事件一直是两条互不相干的时间线。

- Harness 告诉你：第 7 步打算读取哪个路径、准备调用什么工具、预期失败后如何回滚。
- Windows 事实告诉你：哪个 PID 在什么时间创建了文件句柄、读写了多少字节、连接了哪个端点、启动了哪个子进程。

单看前者，我们只能知道“它说要做什么”；单看后者，我们只能知道“某个进程做了什么”。CausativeLens 加入的是中间那一层：断言、系统事件和履约判定。

一个最小例子是：

```text
推理断言：以只读方式访问 C:\work\config.yaml
系统事件：同一进程树在窗口内发生 FileRead
判定：Fulfilled
```

如果窗口内出现同一路径的写类事件，结果就不是一句模糊的“有风险”，而是一个带证据边的 `Deviated`：触发断言、冲突事件、时间、PID、评分、原始引用和采集健康度都能被回溯。

## 二、v0.2.5 的总体架构

系统坚持“一 daemon，两前端”。

```text
Agent / Harness JSONL ──┐
                         ├─ clens-daemon ── 对齐/存储/查询 ── SQLite + .clspool
Windows ETW capture ────┘             │
                                      ├─ clens.exe
                                      └─ clens-gui.exe
```

`clens.exe` 和 `clens-gui.exe` 都是 daemon 的 JSON-RPC 前端。GUI 不链接对齐引擎、存储或 capture crate，也不复制一套业务逻辑；它只是把同一份证据放到更容易操作的窗口里。这条边界由架构测试持续断言。

只有 `clens-capture.exe` 需要管理员令牌。daemon、CLI 和 GUI 都以标准用户运行；产品不安装服务、不加载驱动、不做进程注入。观测是只读的，v0.2.5 不注册 `advise`、`enforce` 或决策写入路径。

## 三、从推理文字到因果断言

推理侧输入是 append-only 的结构化轨迹。v0.2.5 的适配器把不同运行时的日志尽量归一为 `HarnessEvent`，保留未知字段和原始引用。

### 1. 规则层先行

工具调用天然带有结构：

- `read(path)` 编译为 `Read + Path + ReadOnly`；
- `edit(path)` 编译为读前置断言和有序写断言；
- `create/delete/rename` 编译为相应文件操作；
- `connect/bind/listen` 编译为网络端点断言；
- `shell(cmd)` 走受限模板库，识别常见的 `rm`、`mv`、`cp`、`curl`、`ssh` 等命令。

规则层的优点是确定性和可审计：同一输入永远得到同一断言，置信度可以是 1.0。

### 2. 语义层是可选项

自由文本中的“我需要先确认配置，再删除旧文件”可以交给用户显式启用的本地小模型。模型输出必须通过受限 JSON 校验，`raw_quote` 还要逐字包含于输入文本；引用不在原文里就拒绝建立证据关系。语义层的置信度有上限，不会把模型的猜测伪装成系统事实。

Jev、OpenAI-compatible、Anthropic-compatible 和 Ollama 在这一层只做证据锚定的解释，不能修改 Verdict、启动进程或执行干预。

## 四、Windows 事实是怎样进入时间轴的

Windows 采集侧围绕 ETW 设计，重点是四类事实：进程、文件、注册表和网络。

采集事件有自己的全局序列号和 QPC 时间戳。文件事件不保存用户文件内容，只保存元数据；FileObject 表负责把句柄生命周期和路径变化联系起来。路径在热路径上使用 `PathIdx` 驻留，减少重复字符串分配。

多个 provider 和多个 CPU buffer 会带来乱序，所以对齐前需要经过有界的重排窗口。水位线推进后，窗口关闭、断言升级和反向归因才会发生。迟到事件不能偷偷改写原始时间；系统会把乱序和丢失作为健康度的一部分呈现。

高频原始明细适合进入 `.clspool` 列式块，SQLite 保存索引、断言、Verdict 和证据边。这样查询“为什么修改了 `config.yaml`”时，先通过索引定位候选链，再按需读取明细，而不是把每个大 payload 都塞进数据库行。

## 五、三元对齐：进程、时间、语义

对齐不是关键词搜索，而是四维评分：

```text
score = process + time + semantic + path
```

- **进程归属**：事件 PID 是否属于断言主体的进程树；
- **时间邻接**：事件是否落在断言窗口和水位线允许的范围；
- **语义模板**：Read、Write、Delete、Connect 等断言是否与 ETW 事件同族；
- **目标匹配**：路径、注册表键、主机、端口和协议是否匹配。

达到阈值的候选事件成为证据边；中间分数保留为 `Partial` 供人工复核；窗口结束仍无可见证据时是 `Unobserved`。如果采集有 buffer loss、capture 未连接或解码未知，界面会显示“证据不可见”，不会把它包装成“确定没有发生”。

这套设计对工程师很重要：它允许我们区分“没有发生”和“没有看见”。

## 六、why 查询返回什么

`why` 不是自由生成答案，而是受限路由：确定性识别 `why/when/what-if`，抽取路径、端点和 step，再执行结构化查询。无法命中模板时，固定提示用户使用 `clens why --path <p>`。

回答固定为五段：

1. 触发断言：原始引用和 step；
2. 证据事件链：seq、时间、PID、操作和目标；
3. 履约判定与因果断点；
4. 反向归因：事件还被哪些断言吸收；
5. 置信度与采集健康度。

这套输出既适合人看，也适合 `--json` 被 CI 和其他工具消费。

## 七、GUI 为什么从 Graph + Settings 扩成七个工作区

v0.2.5 的 GUI 按用户旅程导航：

1. **Sessions**：会话列表、健康度和摘要；
2. **Observe**：实时监听、时间线和采集状态；
3. **Investigate**：断点、双泳道、Why 和证据卡；
4. **Replay**：播放、步进、断点书签；
5. **Compare**：两次观测的断言、判定和断点差异；
6. **Assist**：带证据引用的可选模型分析；
7. **Intervention**：当前锁定，只展示未来方向。

菜单栏、快捷键和工作区都服务于同一条路径：先找到会话，再看到断点，最后回到证据。健康度胶囊常驻显示 `EventsLost`、TDH fallback、quarantine、dropped 和 late reorder；GUI 不用漂亮的空图遮掩数据不可见。

## 九、如何开始

安装后先做自检：

```powershell
clens --version
clens doctor --json
```

GUI 中打开 **监听**，选择你的 Agent 模板，再选择日志或项目目录。当前版本兼容 17 家产品模板，并额外提供 WorkBuddy 国内版、国际版、DeepSeek Harness 和 Others。未知版本不会被名字强制拒绝，但健康度会告诉你结构是否真正识别。

需要查询时：

```powershell
clens why --path C:\work\config.yaml
clens timeline --json
```

如果选择了 Jev 或其他兼容 API，辅助分析只解释已有证据链，不会替你补造证据。

## 十、诚实的边界

v0.2.5 是 beta/test release。x64 本机安装器、doctor、GUI smoke、卸载和重装已经留下证据；ARM64 运行矩阵、干净 VM、重启验证、Trusted Signing 和完整内核采集性能仍是独立门槛。没有真实 ETW 连接时，CausativeLens 会显示“未观测到”或“证据不可见”，不会把 Harness 日志冒充内核事实。

CausativeLens 不是 EDR，不替代 Agent runtime，也不是一个会替你做决定的自动驾驶层。它更像一盏放在系统边缘的小灯：照见 Agent 许下的承诺，也照见操作系统留下的脚印，然后把判断权交还给工程师。
