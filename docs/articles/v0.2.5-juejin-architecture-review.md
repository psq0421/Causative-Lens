# 如果把 CausativeLens 交给一位冷静的评审：v0.2.5 架构拆解、自我审视与一个还没揭开的问号

> 这是该项目迄今最大的一次更新。

如果把 CausativeLens v0.2.5 放到一个不认识作者的评审桌上，第一眼看到的可能不是“又一个 Agent 监控工具”，而是一种有点拧巴、但值得继续追问的尝试：它不满足于列出 Agent 访问过哪些文件，而是想验证 Agent 自己说出的意图有没有被系统行为兑现。

这句话听起来很像产品宣言，工程上却是一个相当麻烦的问题。因为“它说了什么”通常在 Harness 日志里，“它做了什么”通常在操作系统轨迹里，中间隔着进程树、时间戳、路径、工具语义、缓冲区乱序和一堆会在凌晨两点突然出现的边界情况。

下面假装这不是我写的项目，站在半个第三方评审的角度，把它拆开看一遍：哪些架构决策是必要的，哪些地方体现了工程纪律，哪些地方仍然像一座脚手架，哪些悬念还没有资格被写成“已经解决”。

## 一、先定义它到底在验证什么

CausativeLens 的最小命题是：

```text
Agent 意图  ->  因果断言  ->  系统事实  ->  履约判定
```

例如 Agent 在第 7 步说：

```text
“我需要以只读方式读取 config.yaml 来确认端口。”
```

系统不会直接把整段文本交给一个大模型，让模型自由发挥解释。规则层会把工具调用或受限文本编译成结构化断言：

```text
op       = Read
path     = C:\work\config.yaml
io_mode  = ReadOnly
expect   = MustHappen
span     = harness step 7
```

Windows 采集侧则产生另一种结构化事实：某个 PID 在某个 QPC 时间点创建了文件访问、读取了多少长度、是否出现写类事件，进程是否属于 Agent 的子树。

最终的输出不是“系统发生过 FileRead”，而是：

```text
断言：第 7 步要求只读 config.yaml
证据：PID 4312 在窗口内对同一路径发生 FileRead
结果：Fulfilled
```

如果同一窗口内出现 FileWrite，判定就可能是 `Deviated`。如果没有证据，但采集丢过 buffer，结果不是“它肯定没读”，而是“证据不可见”。这几个词的差别，是产品能否用于工程调试的分水岭。

## 二、顶层架构：一个 daemon，两扇窗户，一把高权限钥匙

从进程拓扑看，系统被拆成三个层次：

```text
                    ┌──────────────────────┐
Harness JSONL ─────>│                      │
                    │    clens-daemon      │──── SQLite / .cllens
ETW capture ───────>│  tail / align / query│──── .clspool / health
                    │                      │
                    └──────────┬───────────┘
                               │ Named Pipe JSON-RPC
                    ┌──────────┴───────────┐
                    │                      │
               clens.exe              clens-gui.exe
                 CLI                      GUI
```

这里最关键的不是进程数量，而是依赖方向：CLI 和 GUI 都请求 daemon，GUI 不直接连接 core、storage 或 capture crate。这样做有三个实际好处。

第一，命令行和图形界面不会各自算一遍履约结果。两个前端可以有不同的交互方式，但应该看到同一张证据图。

第二，daemon 是会话生命周期的中心。它负责会话票据、Harness tail、capture 连接、断言池、对齐循环和查询路由。GUI 关闭时，观测不必跟着窗口一起蒸发。

第三，特权面被压缩到 `clens-capture.exe`。它才可能因为 ETW 内核 provider 请求 UAC；daemon、CLI、GUI 都保持标准用户权限。项目不安装 Windows 服务、不加载驱动、不注入目标进程，这不是安装器宣传词，而是攻击面控制策略。

站在评审角度，这个拆分是合理的，但它也带来一个代价：跨进程数据面必须真正可靠。只要 capture 到 daemon 之间还依赖容易阻塞或重复序列化的桥，架构图画得再漂亮，也只是把瓶颈换了一个位置。

## 三、数据模型：三个一等公民和一条不能乱跳的证据链

核心数据模型收敛为三类：`SysEvent`、`Assertion`、`Verdict`。

### 1. SysEvent：系统发生了什么

`SysEvent` 是纯数据结构，不携带 Windows API 对象，也不在里面藏文件内容。它至少包含：

- `schema_v`：跨版本演进；
- `seq`：capture 侧全局序列号；
- `ts_qpc`：系统单调时钟域；
- `pid/tid`：进程和线程身份；
- `kind`：进程、文件、注册表、网络事件；
- `payload`：路径索引、访问掩码、长度、端点等元数据。

文件读写只保存元数据，不读取用户文件缓冲区。这既是性能决策，也是隐私边界：工具需要知道“写了哪个文件”，通常不需要把文件内容搬进观测数据库。

### 2. Assertion：Agent 承诺了什么

`Assertion` 记录的是可验证的声明，而不是完整思维链。它包含操作类型、目标模式、I/O 模式、期望、来源 span、置信度和原始引用。

断言必须能被机械匹配。`Read`、`Write`、`Delete`、`Connect` 这些操作适合进入模板表；无法确定的自由文本可以保留为弱匹配，但不能伪装成精确事实。

### 3. Verdict：证据支持哪一种结论

`Verdict` 把一条断言映射到履约状态：

```text
Fulfilled   已找到足够强的证据
Deviated    找到冲突证据
Unobserved  窗口关闭仍没有可见证据
Partial     有候选，但证据不足以完全确认
```

这三层之间不能跳步。Harness 文本不是 SysEvent，SysEvent 也不自动等于某条 Assertion 的证据。中间的对齐引擎负责把“可能相关”变成带评分的 EvidenceEdge。

## 四、采集层：ETW 不是一条日志，而是一组有脾气的时间线

Windows ETW 的麻烦在于，它不是一个简单的 `readline()` 文件。不同 provider 有不同事件语义；多个消费线程会产生跨线程乱序；FileCreate、FileSetInfo、FileWrite 和 FileClose 之间还要靠 FileObject 生命周期拼出路径关系。

CausativeLens 的采集计划拆成四步：

1. 建立 Process、File、Registry、Network 四类 provider 会话；
2. 使用 `EVENT_RECORD` 和 TDH 获取事件字段；
3. 用手工布局解码覆盖高频事件，TDH 作为正确性兜底；
4. 经过 QPC 时间排序、FileObject 路径表、序列号和 spool/ring 通道后交给 daemon。

### 1. 为什么要有手工解码和 TDH 双路径

TDH 的优点是通用、正确、对 schema 变化更有韧性；缺点是每条事件动态查询类型信息的成本很高。手工布局快路径则反过来：对少量高频 provider/opcode 使用无分配 cursor 解析，速度更可控，但必须承担字段布局变化的风险。

所以合理的工程姿势不是“TDH 慢，全部手写”，而是：

```text
已知高频布局 -> 手工快路径
未知/变化布局 -> TDH fallback
两者对同一 fixture -> oracle 对照
```

如果没有 TDH 对照测试，手工解码只是“看起来像解码”；如果只有 TDH，又很难接近高吞吐目标。两条路径必须被同一组 golden fixture 约束。

### 2. FileObject 表为什么不能省

只看到 `FileRead` 还不够。ETW 事件中经常先出现句柄或对象，再在后续事件里体现路径和操作。FileObject 表负责：

```text
创建 -> 建立对象到路径映射
重命名 -> 更新映射
读写 -> 通过对象找到路径
关闭 -> 清理映射
```

这张表如果做错，后面的因果图会出现最让人哭笑不得的结果：Agent 明明读的是 `config.yaml`，报告却说它写了一个设备路径。系统没有“理解错”，是我们丢了上下文。

### 3. ring、spool 和恢复

热路径使用内存映射 ring，接近满载时溢写 `.clspool`。帧带 magic、schema、长度、CRC 和序列号；daemon 重启后从消费位置继续读取，坏帧和 gap 必须可见。

这里有一个很实际的判断标准：capture 崩溃、daemon 重启、机器负载升高以后，系统是“少了一段并明确告诉你少了”，还是“悄悄少了一段但图还画得很完整”。后者在演示里很漂亮，在审计里很危险。

## 五、对齐引擎：不是关键词搜索，是四个分数的合奏

候选事件和断言之间的匹配使用四维评分：

```text
score(a, e) =
    w_p * process(a, e)
  + w_t * time(a, e)
  + w_s * semantic(a, e)
  + w_g * path(a, e)
```

- `process`：事件 PID 是否属于断言主体的进程树；
- `time`：是否接近断言窗口中心；
- `semantic`：断言操作与事件 kind 是否命中模板；
- `path`：路径、注册表键、端点是否精确或弱匹配。

事件进来时，倒排索引只触碰相同 PID/事件族的活跃断言；断言进来时，则扫描窗口内既有事件。水位线由系统事件时间、乱序窗口和断言延迟共同决定。

这让流式判定具备两个重要性质：

- 新事件可以把 `Partial` 增量升级为 `Fulfilled`；
- 窗口关闭后，`MustHappen` 没有证据才会进入 `Unobserved`。

`MustNotHappen` 更麻烦，它不是“现在没看到”就算通过，而要等约束窗口结束，同时确保采集可见性没有被丢失和过滤打断。这个地方很容易被产品演示简化，也很容易在生产里产生误报。

## 六、为什么查询必须受限

“为什么它修改了 config.yaml？”看起来像自然语言问题，实际应该被翻译成确定性的查询：

```text
意图 = why
实体 = path(config.yaml)
查询 = 断言 -> 证据边 -> Verdict -> 反向归因 -> 健康度
```

v0.2.5 不让 LLM 直接生成 SQL，也不让它决定事实。模板无法命中时，系统退回 `clens why --path <p>` 的提示。这样做少了些魔法，多了些可复现性。

可选的 Jev 或兼容模型只负责解释已经提交的证据链。引用必须存在于证据链中，路径默认脱敏，API key 不落盘。模型可以把一张很硬的图解释得更容易读，但不能从空气里变出一条 FileWrite。

## 七、GUI：窗口不是第二个引擎

v0.2.5 的 GUI 按调查旅程拆成七个工作区：

```text
Sessions -> Observe -> Investigate -> Replay -> Compare -> Assist -> Intervention
```

这不是为了凑菜单。每个工作区都对应一类用户问题：

- Sessions：我有哪些会话？健康度怎样？
- Observe：现在有没有新轨迹？
- Investigate：断点在哪里？证据是什么？
- Replay：这一步之前和之后发生了什么？
- Compare：两次运行差异在哪里？
- Assist：能否用模型帮我解释现有证据？
- Intervention：未来要不要允许系统执行动作？

最后一个工作区目前必须锁定。把“规划中的干预”做成一个灰色入口，比做一个会偷偷执行策略的半成品安全得多。

GUI 的性能约束也不能只看截图：单窗口、单 daemon 连接，Canvas 为主，增量合并，虚拟化限制 DOM 节点，图形更新要有 `graph.delta` 边界。否则十万事件到来时，前端会从“极简”变成“极慢”，那就不是极客，是极刑。

## 八、站到评审桌对面：这套架构哪里还不够

如果这是一份第三方评审报告，我会把下面几项写成黄色甚至红色：

### 1. 真实 ETW 证据必须和合成 fixture 分开

合成 JSON fixture 很适合验证对齐算法，却不能证明真实内核事件已经从 provider 走到了履约图。发布文档必须区分：

```text
算法测试通过 != 真实采集闭环通过
```

这不是措辞问题，而是证据来源问题。

### 2. 吞吐数字必须测完整链路

只测 decoder 或 spool recovery 不够。真正需要测的是：

```text
EVENT_RECORD -> decode -> ring -> daemon -> reorder -> align -> queryable
```

如果中间仍有 JSON 序列化、管道阻塞或重复分配，单点 benchmark 的漂亮数字不能替代端到端数字。

### 3. attach 和子孙进程语义需要运行证据

PID filter、rundown 和父子进程映射可以在代码中有入口，但“已经覆盖目标进程后来启动的所有子孙进程”必须由 Windows runner 和可重放日志证明。静态代码路径不等于运行态事实。

### 4. 断言模板越多，误匹配面越大

增加资源预算、网络白名单、数据流和幂等模板会提升覆盖率，也会增加语义相似但实际意图不同的情况。模板库不是越大越好，必须有互斥样本、负例和人工标注，否则只是把不确定性藏到更厚的表格里。

### 5. 持久化恢复是产品能力，不是数据库选型

SQLite WAL、`.cllens` 和 FTS5 解决的是存储机制；真正的验收问题是 daemon 崩溃后是否能恢复会话、履约图、manifest 哈希链和 why 证据。重启前后输出必须可比，不能只证明“数据库文件还在”。

这些问题不会推翻整体架构，但会决定它究竟是一个很有想象力的原型，还是一个能进入 Agent 调试日常的工具。

## 九、代码规模与工程分工

按 v0.2.5 标签对应提交统计，排除文档、依赖元数据、生成目录、`target`、`dist` 和 `.git`：

- Rust 生产代码：12,589 行；
- Rust 测试、bench、fuzz：717 行；
- GUI 前端：1,500 行；
- 安装器与脚本：1,062 行；
- 可执行代码与脚本：15,868 行；
- 加上 CI workflow：15,963 行。

这组数字不能证明质量，却能帮助评审判断工程重心：核心仍然在 Rust 和 Windows 采集/对齐边界，GUI、安装器、测试和 CI 也各自承担自己的风险。

## 十、悬念留在这里

假设一条断言已经被系统事件验证：Agent 说只读，系统也确实只读。下一步问题就会变成：

```text
如果第 N 步换一种推理路径，系统副作用会不会改变？
```

这是反事实回放。它不能靠简单复制一份 JSON 完成，因为网络请求、进程启动、非幂等写入和外部服务状态都可能改变结果。理想状态下，系统可以把“实际发生过的轨迹”与“声明式工具动作的轻量模拟”叠加起来，告诉工程师哪条推理分支会触发写入、哪条会触发网络请求。

这也是 CausativeLens 目前最值得继续追的问号：它现在试图把“说过的话”和“留下的脚印”焊在一起；下一步，能不能在不假装重跑现实的前提下，推演另一条路会留下什么脚印？

我是一名新人，这个项目的核心架构、Rust 代码和 Windows 约束是我边学边做的；前端部分确实借助了不少 Codex，尤其是界面脚手架、交互拆分和调试整理。它没有替我解决 ETW 语义、证据边界和工程验收，但帮我把一些原本会卡很久的前端工作往前推了一段。

所以如果你在代码里看到还不够老练的地方，不必客气。欢迎把它当成一个新人递出的架构草图：图上有路，有桥，也有几处还没铺完的河。真正有意思的地方，可能正是下一次事件进入 ring 之后，谁先被证明——是 Agent 的承诺，还是我们的假设。
